1. 
Introduction 
1.1 
Purpose 
     This Software Requirements Specification (SRS) document describes the requirements of the 
Smart Parking Management System, a web-based application developed to simplify parking 
management. The system enables users to search for available parking spaces, reserve slots, make 
secure online payments, and access parking areas using QR code-based authentication. It also 
provides administrators with tools to manage users, parking lots, bookings, payments, and system 
analytics. The primary objective of this document is to define the complete functionality, performance 
requirements, constraints, and interfaces of the system, serving as a comprehensive guide for 
developers, testers, project managers, and other stakeholders throughout the software development 
life cycle. 
1.2 
Intended Audience  
    This document is intended for the users and stakeholders of the Smart Parking Management                   
System, including parking lot administrators, and parking management personnel who will use, 
operate, and maintain the system. It is also intended for system administrators responsible for       
managing parking spaces, user accounts, bookings, payments, QR code operations, and overall 
system monitoring. 
    In addition, this document serves as a reference for developers, testers, project supervisors, 
project managers, and other stakeholders involved in the analysis, design, implementation, testing, 
deployment, and maintenance of the system. It provides a common understanding of the system 
requirements and ensures effective communication and coordination among all parties throughout the 
software development life cycle. 
1.3 
Intended Use 
   This Software Requirements Specification (SRS) document is intended to serve as the primary 
reference for the analysis, design, development, testing, deployment, and maintenance of the Smart 
Parking Management System. It defines the functional and non-functional requirements of the system 
and provides a common understanding of the expected behaviour, features, and constraints. 
   The document will be used by developers during implementation, testers for system verification and 
validation, project managers for planning and monitoring project progress, and stakeholders to 
ensure that the developed system satisfies the specified requirements. It also serves as a baseline for 
future enhancements, maintenance, and system upgrades.

1.4 
Product Scope 
     The Smart Parking Management System is intended to manage parking-related activities through a 
centralized web-based platform. The system covers user registration, parking lot and slot 
management, slot availability, pre-booking and live booking, QR-based entry and exit, parking 
duration tracking, and payment processing. 
The system also provides administrative functions for managing users, parking lots, slots, pricing, 
and reported parking issues. It maintains relevant booking, parking session, and payment records 
and provides users and administrators with appropriate information based on their access.

2. 
Overall Description 
2.1 
Product Perspective 
     The Smart Parking Management System is based on the concept of efficient parking 
management. The primary stakeholders of the system are Users and Administrators. A user searches 
for available parking slots, reserves a suitable slot, completes the payment, and receives a QR code 
for parking entry and exit. The system maintains booking, payment, and parking records for future 
reference. Administrators manage parking lots, parking slots, users, bookings, payments, and 
incident reports while monitoring the overall parking operations through a centralized platform.

2.2 
Product Functions 
 
Figure 2-DFD 
 
 
The above DFD clearly shows various processes associated with the project and how data flows

The Admin manages the parking lots, parking slots, pricing, and user information. The admin also 
updates slot availability, manages bookings, resolves incident reports, and maintains the parking 
records required for the smooth functioning of the system. 
 
A User registers into the system by providing personal and vehicle details. The user searches for 
available parking slots and can choose either Pre-Booking or Live Booking. For Pre-Booking, the user 
selects a slot, date, and time, pays the required base fare, and receives a booking confirmation along 
with a QR code. For Live Booking, the user selects an available slot and receives a QR code for 
immediate parking entry. 
 
At the parking facility, the QR code is scanned to authorize entry. During exit, the system records the 
parking duration and calculates the total parking charge. If the booking is a Pre-Booking, the 
remaining parking amount is collected after deducting the base fare already paid. If it is a Live 
Booking, the complete parking charge is collected at exit. After successful payment, the system 
updates the booking and payment records and generates a digital receipt for the user.

Non - Functional Features: 
 
The system should be able to scale to 10,000+ users concurrently and shall have a response time of 
≤ 2 seconds for critical functionality. For other functions, the response time shall be ≤ 4 seconds 
during peak periods. Further, the system shall maintain consistent and accurate information, 
particularly for parking slot availability, bookings, parking duration, and payment details, ensuring that 
the information displayed to users reflects the actual system status.

2.5 
Design and Implementation Constraints 
The following Design and Implementation Constraints are applicable for the Smart Parking 
Management System: 
a) The system shall be designed to ensure that a parking slot cannot be assigned to more 
than one user for the same time period. The availability of slots must be checked before 
confirming a booking. 
b) The system shall support both Pre-Booking and Live Booking. Pre-Booking requires the 
user to pay the applicable base fare during reservation, while the remaining parking 
amount shall be calculated and collected at the time of exit. For Live Booking, the 
parking charge shall be calculated based on the actual parking duration and collected at 
exit. 
c) The system shall use QR code-based entry and exit validation. A valid QR code shall be 
associated with the corresponding booking or parking session, and the system shall 
record the entry and exit time to determine the parking duration. 
d) The system shall maintain accurate records of users, vehicles, parking lots, parking 
slots, bookings, parking duration, and payment transactions. Access to administrative 
information shall be restricted to authorized administrators. 
e) The system shall be designed to handle multiple users accessing parking availability 
and booking functionality at the same time without creating duplicate slot allocations or 
inconsistent booking information. 
f) The system shall provide a responsive user interface so that users can access the 
system through commonly used desktop and mobile web browsers. The interface 
should remain usable across different screen sizes. 
g)   The system shall use secure authentication and authorization mechanisms to protect 
user and administrative information. Payment-related operations shall be handled 
through the selected payment gateway, and sensitive payment information shall not be 
directly stored by the system unless required. 
h) The system shall be designed with a simple and intuitive interface so that users can 
easily search for parking slots, make bookings, complete payments, and perform entry 
and exit operations without unnecessary complexity.

2.7 
Assumptions and Dependencies 
Key Assumptions are: 
● The system shall assume that parking lots and parking slots have been registered and 
configured by the Admin before users can make bookings. 
● Users shall be required to register and log in to the system before making a parking 
reservation or accessing their booking and payment information. 
● The system shall support two types of parking: Pre-Booking and Live Booking. Pre-Booking 
allows a user to reserve a slot in advance, while Live Booking is intended for users who 
require parking immediately. 
● For Pre-Booking, the user shall pay the applicable base fare at the time of reservation. The 
remaining parking amount, based on the actual parking duration, shall be calculated and 
paid at the time of exit. 
● For Live Booking, the parking charge shall be calculated based on the actual parking 
duration and shall be paid by the user during the exit process. 
● A parking slot shall not be assigned to multiple active bookings for the same applicable 
period. The system shall check slot availability before confirming a booking. 
● QR codes shall be used for parking entry and exit validation. The QR code shall be 
associated with the relevant booking or parking session and shall be validated before 
recording entry or exit. 
● The system shall record the entry time and exit time of a parking session. The parking 
duration shall be determined from these timestamps and used for calculating the applicable 
parking charge. 
● Online payments shall be processed through the integrated payment gateway. The system 
shall record relevant payment details and payment status required for completing the 
booking or exit transaction. 
● The Admin shall be responsible for maintaining parking lot information, parking slots, pricing 
details, and other administrative information required for operating the system. 
● The system shall assume that users provide valid personal and vehicle information during 
registration and that the information required for booking and payment is available when 
needed.

● The system shall be accessible through supported web browsers and shall be designed to 
work on both desktop and mobile-sized screens. 
● The system shall depend on the availability of the backend server, PostgreSQL database, 
payment gateway, and other external services required for the corresponding functionality. 
● The system shall maintain booking, parking, and payment records for future reference, 
subject to the storage and database constraints of the deployed environment. 
● The system shall not be responsible for physically controlling parking barriers, gates, or 
sensors unless such hardware integration is explicitly included in the project. QR validation 
and parking records shall be handled by the software system.

5. 
Other Nonfunctional Requirements 
5.1 
Performance Requirements 
At the peak, system should be able to scale to 10,000+ users concurrently. The following 
processes are critical and should respond within the specified time under normal operating 
conditions: 
● User Registration/Login ≤ 3 seconds 
● Parking Lot and Slot Search ≤ 3 seconds 
● Slot Availability Check ≤ 3 seconds 
● Pre-Booking Request ≤ 4 seconds 
● Live Booking Request ≤ 4 seconds 
● QR Code Entry/Exit Validation ≤ 2 seconds 
● Payment Request/Confirmation ≤ 5 seconds 
● Booking and Payment History ≤ 4 seconds 
● Report Issue Submission ≤ 3 seconds 
The system shall maintain consistent and accurate information during normal operation. The 
parking slot availability displayed to the user shall reflect the current status of the parking lot, 
including whether a slot is available, occupied, or reserved. Booking, parking duration, and 
payment details shall be updated correctly to ensure that users and administrators always 
receive reliable information. 
 
5.2 
Safety Requirements 
The system shall be designed to ensure the safe and reliable operation of the parking facility. 
The parking lot layout, parking slots, entry and exit points displayed in the system shall 
accurately represent their actual physical locations. The system shall prevent incorrect or 
conflicting slot assignments that could lead to vehicle collisions or unsafe parking conditions. 
The system shall ensure that parking slot information cannot be manipulated or altered by 
unauthorized users. Any changes to parking lot layouts, slot information, or availability shall 
be performed only by authorized administrators. The system shall also ensure that faulty or 
unavailable parking slots(as marked by administrator) are not shown as available for booking. 
 
5.3 
Security Requirements 
The system shall maintain the confidentiality of user, booking, and payment-related 
information. Users shall be provided access only to their own personal and parking-related 
information, while administrators shall be permitted to view only the basic information required 
for managing the parking system. Authentication and authorization shall be implemented to 
prevent unauthorized access to the system. Access to sensitive information and system 
functions shall be restricted based on the user's role, and unauthorized users shall not be 
allowed to modify booking, parking, or payment information.

5.4 
Software Quality Attributes 
The Key Software Quality Attributes are Reliability, Usability, Security, and Maintainability. 
Since the system handles parking bookings, slot availability, and payment transactions, it 
needs to be highly reliable and consistent. The system should provide a simple and user-
friendly interface so that users can easily search, book, make payments, and complete 
parking entry and exit operations. Security is important to protect user and payment-related 
information from unauthorized access. The system should also be maintainable, allowing 
administrators and developers to manage parking information and make necessary system 
updates efficiently. 
 
 
5.5 
Software Back-ups and Redundancy 
The system data shall be backed up every night with a retention cycle of 30 days. The backup 
shall include user, parking, booking, parking session, and payment-related data to provide a 
provision for recovery in case of data loss or system failure. 
The backup shall be periodically restored in a separate test environment to verify the 
completeness and correctness of the backup. The test data shall be removed after successful 
verification. A redundant copy of the backup shall also be maintained separately from the 
primary system to reduce the risk of data loss due to system failure. 
 
6. 
Summary 
This document details the Software Requirements Specification (SRS) for the Smart Parking 
Management System. The document has 5 sections. The first section, Introduction, describes 
the purpose of the document, intended audience, intended use, product scope, definitions and 
acronyms, and an overview of the system. 
Section 2, Overall Description, provides a detailed description of the system. It covers the 
product perspective, product functions, user classes and characteristics, operating 
environment, design and implementation constraints, user documentation, and assumptions 
and dependencies. 
Section 3, External Interface Requirements, describes the interfaces of the system, including 
user interfaces, hardware interfaces, software interfaces, and communication interfaces. 
Section 4, System Features, describes the system feature priority matrix and the functional 
requirements of the Smart Parking Management System. The functional requirements define 
the major operations and services provided by the system. 
Section 5, Other Nonfunctional Requirements, describes the nonfunctional requirements of 
the system. It includes performance requirements, safety requirements, security requirements, 
software quality attributes, software backups and redundancy.
